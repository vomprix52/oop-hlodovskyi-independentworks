# Звіт до самостійної роботи №10

Тема: колекції в практиці ООП, інвертований індекс і вимірювання продуктивності.

## 1. Опис реалізації

### Класи проєкту

- `Document`: документ з `Id`, `Title` і `Content`, як в умові.
- `TextProcessor`: розбиття тексту на слова (`Tokenize`), видалення стоп-слів (`RemoveStopWords`) і метод `Normalize`, який робить обидва кроки.
- `InvertedIndex`: сам індекс з методами `AddDocument`, `SearchSingleWord`, `SearchMultipleWords` і `SearchAnyWord`.
- `SampleData`: п'ять тестових документів з умови і генератор великих наборів.
- `PerformanceTest`: порівняння лінійного пошуку з пошуком через індекс.
- `Program`: інтерактивний пошук.

### Обробка тексту

Для розбиття тексту на слова я використав `Regex` з шаблоном `\w[\w#+]*`. Текст спочатку переводиться в нижній регістр, а регулярний вираз вибирає слова і відкидає пунктуацію. Звичайний шаблон `\w+` з методичних вказівок я трохи змінив. З ним `C#` перетворювався б на `c`, і тоді запит `c#` знаходив би все, де є окрема літера «c». У моєму шаблоні слово має починатися з літери чи цифри, а символи `#` і `+` дозволені всередині, тому `c#` і `c++` залишаються цілими.

```csharp
private static readonly Regex WordPattern = new Regex(@"\w[\w#+]*", RegexOptions.Compiled);

public static IEnumerable<string> Tokenize(string text)
{
    foreach (Match match in WordPattern.Matches(text.ToLowerInvariant()))
    {
        yield return match.Value;
    }
}

public static IEnumerable<string> Normalize(string text)
{
    return RemoveStopWords(Tokenize(text));
}
```

Стоп-слова (`a`, `the`, `is`, `and` тощо) в індекс не потрапляють, бо вони є майже в кожному документі і для пошуку нічого не дають. Через це в індексі 31 унікальне слово, а не 45, як у прикладі з умови. Точне число залежить від правил розбиття на слова: без видалення стоп-слів їх було б 37, а якби індексувалися ще й заголовки, то 44.

Найважливіше: метод `Normalize` використовують усі способи пошуку. Індекс через нього обробляє документи і запити, а лінійний пошук обробляє документи. Тому порівняння чесне: обидва способи шукають за однаковими правилами і знаходять однакові документи.

### Індекс

```csharp
// Слово -> Множина ID документів
private Dictionary<string, HashSet<int>> _index;

// ID -> Документ (для швидкого отримання)
private Dictionary<int, Document> _documents;
```

`AddDocument` зберігає документ у `_documents` і для кожного слова з тексту додає `Id` документа в множину цього слова. Якщо слово трапляється в документі кілька разів, `HashSet` не додасть `Id` вдруге. Документ з уже зайнятим `Id` додати не можна, для цього я використав `TryAdd`.

Пошук за кількома словами (AND) зроблено через `IntersectWith`, а пошук за будь-яким словом (OR) через `UnionWith`:

```csharp
public List<Document> SearchMultipleWords(params string[] words)
{
    List<string> terms = NormalizeQuery(words);
    if (terms.Count == 0)
    {
        return new List<Document>();
    }

    HashSet<int>? result = null;
    foreach (string term in terms)
    {
        if (!_index.TryGetValue(term, out HashSet<int>? ids))
        {
            return new List<Document>();
        }

        if (result is null)
        {
            result = new HashSet<int>(ids);
        }
        else
        {
            result.IntersectWith(ids);
        }
    }

    return ToDocuments(result!);
}

public List<Document> SearchAnyWord(params string[] words)
{
    HashSet<int> result = new HashSet<int>();
    foreach (string term in NormalizeQuery(words))
    {
        if (_index.TryGetValue(term, out HashSet<int>? ids))
        {
            result.UnionWith(ids);
        }
    }

    return ToDocuments(result);
}
```

На дві речі тут легко не звернути уваги:

1. Перед `IntersectWith` я роблю копію множини з індексу (`new HashSet<int>(ids)`). `IntersectWith` змінює ту множину, на якій його викликають. Без копії після першого ж пошуку в індексі зіпсувалися б дані.
2. Якщо одного зі слів немає в індексі, метод одразу повертає порожній список, бо перетин з порожньою множиною завжди порожній, і далі можна не рахувати.

`HashSet` не зберігає порядок, тому в кінці документи сортуються за `Id`.

### Інтерактивний пошук

Програма приймає запити з клавіатури:

- слова через пробіл шукають документи, де є всі слова (AND);
- `or` і слова шукають документи, де є будь-яке слово (OR);
- `perf` запускає вимірювання продуктивності;
- `exit` завершує програму.

З завдань з зірочкою я зробив підсвітку: слова із запиту в знайдених документах виводяться жовтим кольором.

## 2. Як проводилися вимірювання

- Документи генеруються з п'яти базових: текст одного з них плюс 5 випадкових слів зі словника. `Random` має фіксоване зерно, тому дані однакові при кожному запуску.
- Лінійний пошук для кожного документа викликає `TextProcessor.Normalize` і перевіряє, чи є серед слів шукане. Так, як у прикладі з умови.
- Час побудови індексу я вимірював окремо від пошуку, бо індекс будується один раз, а шукати можна багато разів.
- Один пошук через індекс триває менше мікросекунди, а `Stopwatch` таке точно не виміряє. Тому пошук через індекс повторюється 10 000 разів, а лінійний стільки разів, щоб загалом обробити близько 50 000 документів. Час ділиться на кількість повторів.
- Перед вимірюваннями всі операції виконуються вхолосту. .NET спочатку запускає неоптимізований код і оптимізує його лише після кількох десятків викликів. Без прогріву перші рядки таблиці були б неправдиво повільними. Я це перевірив: без прогріву 10 000 документів шукалися лише в 4,6 раза довше за 1000, а з прогрівом приблизно в 10 разів, як і має бути.
- Програма запускалася в режимі Release (`dotnet run -c Release`), бо в Debug оптимізації вимкнені.

Я перевіряв два слова:

- `python` є в 40% документів, тобто результатів багато;
- `rust` немає в жодному документі.

Для кожного рядка програма перевіряє, що обидва способи знайшли ті самі документи. В усіх рядках вийшов збіг.

## 4. Аналіз результатів

**Лінійний пошук росте пропорційно кількості документів.** Для `python` 10 документів шукаються за 12,8 мкс, а 10 000 за 13 024 мкс. Документів у 1000 разів більше, і час теж приблизно в 1000 разів більший. Це O(n): кожен документ треба розбити на слова і переглянути.

Для `rust` лінійний пошук повільніший, ніж для `python`. `Contains` зупиняється, щойно знайде слово. Для `python` це відбувається десь посередині документа, а для `rust` доводиться переглядати кожен документ до кінця.

**Пошук через індекс для `rust` майже не залежить від кількості документів:** 0,14 мкс для 10 документів і 0,24 мкс для 10 000. Це і є O(1): одне звернення до `Dictionary`, яке не залежить від того, скільки документів в індексі.

**Пошук через індекс для `python` трохи росте:** від 1,4 до 72 мкс. Сам пошук слова в словнику так само O(1), але потім треба зібрати всі знайдені документи в список і посортувати їх. Для 10 000 документів таких 4000. Тобто час пошуку через індекс залежить не від кількості документів, а від кількості результатів. Навіть так він у 180 разів швидший за лінійний.

**Побудова індексу коштує приблизно як 2–3 лінійні пошуки.** Це логічно, бо і лінійний пошук, і побудова індексу розбивають на слова весь текст усіх документів. Побудова ще й додає слова в словник, тому трохи довша.

## 5. Висновки

**Поріг вигідності індексу.** За моїми вимірюваннями індекс окупається вже після 2–4 пошуків, і це майже не залежить від кількості документів. Отже:

- якщо по документах шукають один раз (наприклад, одноразова перевірка), то індекс будувати не варто, лінійний пошук буде швидшим;
- якщо пошуків хоча б кілька, індекс вигідніший;
- якщо пошуків багато, як у пошуковій системі, різниця величезна. На 10 000 документах лінійний пошук займає 13–20 мс, а пошук через індекс менше 0,1 мс.

Для маленьких наборів (10 документів) обидва способи займають мікросекунди, і людина різниці не помітить. Але вже на 10 000 документах 1000 запитів лінійним пошуком займуть 13–20 секунд, а через індекс менше 0,1 секунди.

Треба враховувати й те, що індекс займає додаткову пам'ять: для кожного слова зберігається множина номерів документів. І при зміні документа індекс треба оновлювати.

**Чому `Dictionary<string, HashSet<int>>` добре підходить для індексу.** `Dictionary` за O(1) знаходить слово. `HashSet` не дає номеру документа повторитися, коли слово кілька разів трапляється в одному тексті. Крім того, у `HashSet` є готові операції над множинами: `IntersectWith` для AND і `UnionWith` для OR, і не треба вручну писати вкладені цикли.

**Чому важлива однакова нормалізація.** Якби лінійний пошук порівнював, наприклад, з урахуванням регістру або не прибирав пунктуацію, то `C#,` у документі 5 не збігся б з `c#`. Тоді способи знаходили б різну кількість документів, і порівнювати їхню швидкість не було б сенсу, бо вони робили б різну роботу. Тому в моїй програмі обидва способи використовують один метод `TextProcessor.Normalize`, і програма перевіряє збіг результатів.

**Обмеження простої реалізації:**

- **немає ранжування:** документ, де слово трапляється 10 разів, і документ, де воно трапляється один раз, мають однакову вагу;
- **немає стемінгу:** `language` і `languages` вважаються різними словами. Тому запит `programming language` не знайшов документ 5, хоча він теж про мови програмування;
- **немає пошуку фраз:** індекс не зберігає позиції слів, тому не можна знайти точну фразу `programming language`, тільки документи, де є обидва слова в будь-якому місці;
- **стоп-слова не шукаються:** запит `the` нічого не знайде;
- **індекс тільки в пам'яті:** після закриття програми його треба будувати заново.
